1. Introduction

1.1 Purpose

This document describes the design, components, behaviour and technical implementation of VeriTrace, a prototype system that lets any consumer verify whether a physical product is genuine by scanning a QR code, and lets businesses in a supply chain record every custody transfer of that product on a blockchain. It is intended for developers, technical reviewers, maintainers and the client's technical stakeholders.

1.2 Problem Statement

Counterfeit goods (electronics, pharmaceuticals, cosmetics, luxury items) are routinely sold with convincing packaging. Traditional labels and holograms can be copied, and centralised product databases can be edited by whoever controls them. Consumers have no independent way to check where a product came from or whether its record has been altered.

1.3 Solution Summary

VeriTrace anchors a cryptographic fingerprint (SHA-256 hash) of each product's identity data and the complete custody history in a smart contract. A QR code on the product carries the product ID and the fingerprint. When scanned, the backend compares the QR, the product database and the blockchain record, checks the custody history, scan patterns and an ML anomaly model, and returns one of four results: Genuine, Flagged, Suspect or Unverified, together with the reasons and the product's full journey.

1.4 Scope

  • In scope: product registration, QR generation and labelling, two-step custody transfers, sale recording, public verification, role-based administration, reporting, ML anomaly scoring, demo tooling.
  • Out of scope: payment, inventory quantities, iOS, production key management, physical tamper-evident tags.

2.2 Functional Features

  • Product registration with validated form (name, brand, category, batch, serial, manufacture/expiry dates, MRP, origin, description); automatic ID VT-<YYYY>-<NNNNNN>.
  • QR code generation, PNG sharing and A4 label-sheet printing (3 × 7 labels).
  • Two-step custody transfer (initiate → confirm), cancellation, multi-hop distribution, sale recording.
  • Public verification by camera scan or manual ID, with reasons, product details, journey timeline and blockchain references.
  • Role administration mirrored on-chain; account deactivation revokes on-chain rights.
  • Reports: scans per result, recent alerts, products by stage, accounts by role, ML statistics.
  • ML anomaly detection that can raise a result to Flagged (never Suspect) and degrades gracefully.

3. System Architecture

VeriTrace follows a three-tier architecture. The Android app is a thin client; all business logic, blockchain interaction and database access are centralised in the backend. The mobile app never talks to the blockchain directly.

3.1 Component Responsibilities

ComponentTechnologyResponsibility
Mobile appFlutter 3, Dart, flutter_bloc, go_router, dio, mobile_scannerUser interface for all actors; camera scanning; QR rendering, sharing and printing.
Backend APINode.js 20+, Express, ethers v6, firebase-admin, zodAuthentication, authorization, validation, business rules, blockchain transactions, verification, reports.
Smart contractSolidity 0.8.24, HardhatAuthoritative roles, product fingerprints, custody state machine, handoff history, events.
DatabaseCloud FirestoreUser profiles, product metadata, scan log, audit trail, counters, runtime settings.
IdentityFirebase AuthenticationEmail/password sign-in for business users; ID tokens verified by the backend.
ML servicePython, FastAPI, scikit-learnAnomaly score for a product's journey and scan pattern.

3.2 Design Principles

  • Chain as source of truth for roles, custody and fingerprints; Firestore holds descriptive data and logs.
  • Defence in depth: every write is checked by API middleware and again by the contract against msg.sender.
  • Thin client: the app holds no secrets; consumers need neither an account nor a wallet.
  • Single source of truth for rules: one verification module and one hashing function.

6. Smart Contract Design

The contract BlockAuth.sol (Solidity 0.8.24) is the trust anchor. It stores only non-personal data: wallet roles, product keys, fingerprints, custody state and history.

6.1 Data Structures

mapping(address => Role)        roles;

6.3 Product State Machine

6.4 Events and Errors

Each state change emits exactly one event (ProductRegistered, TransferInitiated, TransferReceived, TransferCancelled, ProductSold, plus RoleChanged). The backend matches the n-th event to the n-th handoff to attach transaction hashes and block numbers. Reverts use custom errors (e.g. InvalidTransition, NotCurrentHolder, NotPendingRecipient, ProductAlreadyExists) which the backend maps to readable messages.

7. Backend Design

7.1 Module Structure

7.2 Request Pipeline

  1. CORS and JSON body parsing; request logging.
  2. authenticate: verifies the Firebase ID token and loads the Firestore profile; rejects missing, expired, profile-less or deactivated accounts.
  3. authorize(roles): rejects callers whose role is not permitted (HTTP 403).
  4. Input validation with zod schemas (field-level messages).
  5. Service logic; blockchain writes are signed with the acting user's own wallet.
  6. Uniform error format { error: { code, message, details } }; contract reverts become CHAIN_REJECTED with the decoded reason.

7.3 Custodial Wallets

Each business account receives an Ethereum wallet derived from a backend-held mnemonic at path m/44'/60'/0'/0/<index>. Index 0 is the deployer/admin, indices 1–9 are reserved for demo accounts, and new accounts start at index 10. Wallets with a low balance are automatically funded by the deployer. Transactions are serialized per wallet to prevent nonce collisions.

7.4 Product Identity and Fingerprint

Product IDs are allocated in a Firestore transaction on counters/products. The fingerprint is computed in one function: the identity fields productId, name, brand, category, batchNumber, serialNumber, manufactureDate, expiryDate, countryOfOrigin, manufacturerId are normalised (trimmed strings, empty → null, dates as YYYY-MM-DD), serialised as JSON with alphabetically sorted keys and no whitespace, and hashed with SHA-256. The QR payload is veritrace://verify?id=<productId>&h=<hash>.

8. Verification Engine

All decision logic is in services/verification.js. Each rule produces a reason with a severity; the final status is the most severe level present. This makes the outcome independent of rule order and guarantees that ML (always "warning") can never produce Suspect.

8.1 Rules

CodeSeverity → resultCondition
MALFORMED_PAYLOADUnverifiedNot a VeriTrace QR / invalid ID.
NOT_ON_CHAINUnverifiedID unknown to the contract (never labelled "counterfeit").
QR_HASH_MISMATCHcritical → SuspectQR fingerprint ≠ on-chain fingerprint (forged label).
METADATA_TAMPEREDcritical → SuspectFingerprint recomputed from database ≠ on-chain (record altered).
HISTORY_INCONSISTENTcritical → SuspectReplaying the handoffs does not reproduce the current state, or events ≠ history.
NOT_AT_RETAILwarning → FlaggedStage Manufactured or AtSupplier at time of scan.
TRANSFER_PENDINGwarning → FlaggedA transfer is not yet confirmed.
EXPIREDwarning → FlaggedExpiry date has passed.
EXCESSIVE_SCANS / MANY_DEVICESwarning → FlaggedMore than 10 scans / more than 5 distinct devices (possible clone).
FAST_HANDOFFwarning → FlaggedCustody gap below the configured minimum.
METADATA_MISSINGwarning → FlaggedOn chain but no database record.
ML_ANOMALYwarning → FlaggedML service reports an anomaly.
ON_CHAIN, QR_HASH_MATCH, METADATA_MATCH, HISTORY_CONSISTENT, ML_NORMAL, AT_RETAILER, SOLDokPassed checks shown to the user.

Thresholds have environment defaults and can be overridden at runtime through the Firestore document settings/verification. Every verification, including unverified ones, is recorded in the scans collection.

9. Machine Learning Anomaly Detection

9.1 Purpose

Deterministic rules catch known patterns. The ML service adds a learned, multi-feature view of what a "normal" journey and scan pattern look like, to surface unusual combinations (cloned codes, scripted scan bursts, laundering through many intermediaries, scans of unreleased goods, very old products suddenly scanned).

9.2 Model and Features

FeatureDescription
numHandoffsNumber of custody receipts.
minGapSeconds, meanGapSecondsMinimum and mean time between custody changes (log-scaled).
secondsSinceRegistrationProduct age (log-scaled).
scanCount, distinctDevices, scansLastHourScan pattern including the current scan (log-scaled).
stageCustody stage at scan (ordinal).

The model is a scikit-learn IsolationForest (300 trees) trained on 16,000 synthetic normal journeys plus ~2% injected anomalies. The decision threshold is the 99th percentile of normal training scores. On held-out synthetic data it catches about 92% of injected anomalies with about 1% false alarms.

9.3 Integration

ML results are stored per scan (mlScored, ml), shown in the app's technical details and summarised for administrators in Reports (service status, model version, scans scored, scans flagged).

10. Mobile Application Design

10.1 Architecture

The Android app is built with Flutter using a feature-first structure and the Bloc pattern for state management. Repositories wrap the HTTP API; Blocs/Cubits hold screen state; views render state.

10.2 Navigation and Access

Routing uses go_router with a guard: public routes (home, scanner, verify, login) are open; dashboards require login and the matching role; the backend enforces roles again. After sign-in the user is routed to the dashboard of their role.

11. Data Model

11.1 Entity-Relationship Overview

Personal data (emails, names) exists only in Firebase/Firestore. The blockchain holds wallet addresses, product keys, fingerprints and custody events. Security rules deny all direct client access to Firestore except a signed-in user reading their own profile; all other access goes through the backend using the Admin SDK.

13. Security Design

ThreatControl
Forged / altered QR labelQR fingerprint compared with on-chain fingerprint → Suspect.
Database record tamperingFingerprint recomputed from database compared with on-chain → Suspect.

Unauthorised writesFirebase token + role middleware; contract checks role, holder and recipient of the signing wallet.

Prototype trade-offs: custodial keys derived from one backend mnemonic, open CORS, plain HTTP on the local network and a local single-node blockchain. These are acceptable for demonstration and must be replaced for production (see Section 17).

15. Deployment and Operations

15.1 Operating Procedure

  1. One-time: install Node.js (and optionally Python); run setup.ps1 (dependencies, ML environment, adb, configuration).
  2. Each run: connect the phone by USB and run start-all.ps1. It starts the blockchain, backend and ML windows, redeploys the contract, seeds demo data, installs and opens the app.
  3. Stop with stop-all.ps1. The local chain is ephemeral; each start begins from fresh demo data.

15.2 Configuration

17. Limitations and Future Work

17.1 Limitations

  • A local single-node blockchain demonstrates the mechanism but is not independent evidence; production requires a public or consortium network.
  • QR codes can be copied; cloning is detected heuristically, not prevented.
  • A valid record proves the code was registered, not that the physical item is the registered one.
  • Custodial keys held by one backend are a prototype shortcut.
  • The ML model is trained on synthetic data; real-world accuracy is unknown.
  • Non-identity fields (MRP, description) are not fingerprinted.

17.2 Future Work

  • Deploy to a public L2 or permissioned network; independent verification in the app via a light client or block explorer links.
  • Per-user key custody (HSM/KMS, MPC wallets or account abstraction).
  • Unit-level serialisation with secure elements (NFC) or scratch-off codes revealed at sale.
  • Retraining the anomaly model on real scan data; per-category thresholds.
  • HTTPS deployment, audit-log integrity, iOS client, multi-tenant onboarding.
